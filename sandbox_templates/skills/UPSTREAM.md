# Vendored skills — what is a copy, and what this repo owns

This file is PROSE, hand-maintained. The revisions are **not** here: they live
in [`../VENDORED.lock`](../VENDORED.lock), generated by
`scripts/vendor-tools.sh` from the channel manifest. Two reasons the pin lives
there and this text does not carry it:

- A pin written by hand drifts from the thing it describes, and nothing catches
  it — the content check compares *content*, never the pin. `VENDORED.lock` is
  derived from the manifest the artifacts actually came from, so it cannot
  disagree with them. (This is not hypothetical: the sibling repo's copy of this
  file recorded `myconv` at one revision while its vendored tree matched
  another.)
- A lock file cannot carry the distinction below, which is the part a reader
  needs before editing anything in this directory.

## Vendored vs sandbox-native — the distinction that matters

**Vendored** skills are COPIES. Their source of truth is another repo, they
arrive through the depot channel, and **a local edit here is silently reverted
by the next `just vendor-tools`.** Edit them upstream.

| Name | Kind | Upstream | Arrives via |
|---|---|---|---|
| `myconv` | plugin | `agentic-conventions` → `plugins/myconv/` | channel (`dist/plugins/myconv`) |
| `myclickup` | skill beside a wheel | `myclickup` → `packaging/sandbox/SKILL.md` | channel (`dist/skills/myclickup`) |

`myclickup`'s skill is pair-vendored with its wheel, so the text can never
describe a version the image does not have. The wheel is installed by the
Dockerfile from `sandbox_templates/wheels/`; the skill is converged into every
profile. Both move together or neither moves.

**Sandbox-native** skills — `audit-sandbox`, `web-read` — are owned HERE. This
repo is their source of truth, the channel never touches them, and editing them
in place is the correct thing to do.

A `plugin` entry carries `.claude-plugin/plugin.json` and loads as
`<name>@skills-dir`, so its own skills are namespaced `/<name>:<skill>`. That
shape is also why **no backup may ever be written inside a profile's
`~/.claude/skills/`**: a `<name>.bak.<stamp>` sibling is a second live copy, and
for a plugin-shaped skill the backup wins the name race. Convergence therefore
replaces in place through a staging directory on the same filesystem and keeps
no backups.

## Refresh

```
just vendor-tools          # consume the channel (verifies every hash first)
just tools-check           # has the channel moved ahead of VENDORED.lock?
```

Live profiles converge to this tree on their next `up`. To push a change now
without touching the container:

```
scripts/profile.sh <profile> converge       # policy + skills (no backups kept)
```

Convergence WARNs on both divergence and pruning rather than acting silently,
and a `.sandbox-seeded` manifest scopes pruning to names this repo seeded — so a
skill an agent authored inside a profile survives untouched.

## What vendoring must never do

An artifact must not widen the sandbox by arriving. The channel manifest ships a
*proposed* permission set alongside `myclickup`; `vendor-tools.sh --permissions`
reports that proposal against `sandbox_templates/claude/claude-settings.json`
and **never edits it**. Adopting any part of it is a separate, human decision.
